# Scalability and techno-economics

## Measured prototype performance

`reports/scalability_benchmark.csv` is generated by the packaged code. The verification run performs 12 repetitions after warm-up at 20, 60, and 180 patients. It isolates in-process ranking latency; it does not include network, database, identity, concurrency, or observability overhead.

| Queue size | Mean rank latency | P95 rank latency | Local synthetic throughput |
|---:|---:|---:|---:|
| 20 | 0.711 ms | 1.036 ms | 28,114 patients/s |
| 60 | 1.580 ms | 1.803 ms | 37,983 patients/s |
| 180 | 4.745 ms | 5.394 ms | 37,938 patients/s |

These numbers describe the supplied machine and synthetic workload only. They are not a production service-level objective.

## Scaling architecture

| Stage | Data and compute | Reliability and security | Trigger to advance |
|---|---|---|---|
| Hackathon | One FastAPI process, Streamlit, in-memory patients, SQLite audit | Local synthetic data | Demonstrate complete safe workflow |
| Single-site shadow pilot | Stateless API replicas, managed PostgreSQL, object/log archive, OIDC/SSO, secrets manager | Multi-zone backup, centralized audit, manual fallback | Approved clinical-safety case and stable shadow metrics |
| Production hospital | Event-driven observations, durable queue-state store, blue/green deployment, WAF, full observability | Tested recovery, key rotation, vulnerability management, on-call | Regulatory/procurement approval and validated integration |
| Multi-hospital | Tenant isolation, per-site configuration/versioning, regional event bus, federated analytics | Regional data-residency controls and site-specific kill switch | Proven one-site safety and governance |

Candidate engineering triggers include sustained API P95 above 500 ms, ranking P95 above 250 ms, CPU above 60%, database connections above 70%, or observation-event lag above 30 seconds. Final thresholds must be agreed from workflow needs and load tests.
